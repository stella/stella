# Mobile

The mobile workspace is an Expo app for iOS, Android, and local web previews.
It uses Expo Router with typed routes and React Compiler enabled.

## Quickstart

> [!NOTE]
> The app runs in its own development client (`stella Dev`), built on your Mac
> the first time and again only when its native code changes. You need Xcode
> with an iOS simulator runtime (Xcode > Settings > Components) and CocoaPods
> (`brew install cocoapods`).

From the repository root:

```sh
bun run agent:up     # the local stack, seeded, in the background
bun run mobile:sim   # the app on an iPhone simulator, against that stack
```

`mobile:sim` reuses a booted iPhone simulator or boots one, builds and
installs the development client when it is missing or stale, starts Metro on a
free port and opens the app with the stack's API as its server. Sign in with
`test@stella.dev`, the seeded owner with matters and documents; the
local sign-in page fills in the emailed code. Ctrl-C stops Metro, and the
simulator too when the run booted it. `bun run agent:down` stops the stack.

Two things can get in the way on a first run:

- Expo's developer menu opens with an introduction sheet that takes the first
  taps. Continue and close it.
- A sign-in sheet left open from an earlier session carries an expired signed
  request, so sending the code fails. Cancel it and start signing in again.

## Builds

`app.config.ts` defines three builds that install side by side, each with its
own name, bundle identifier and sign-in redirect scheme:

| `APP_VARIANT`           | Name           | Identifier                |
| ----------------------- | -------------- | ------------------------- |
| `development` (default) | stella Dev     | `app.stll.mobile.dev`     |
| `preview`               | stella Preview | `app.stll.mobile.preview` |
| `production`            | stella         | `app.stll.mobile`         |

## Development

From the repository root:

```sh
bun --filter @stll/mobile ios
bun --filter @stll/mobile android
bun --filter @stll/mobile web
```

Sign in with the address of a stella server. Plain http is accepted only for a
simulator's or emulator's own host, so a local stack is reached at
`http://localhost:<api port>` (or `http://10.0.2.2:<api port>` from an Android
emulator); a phone needs an https server.

Agents drive the app on a simulator against the local stack with the
`test-mobile` skill (`.ai/local-skills/test-mobile/SKILL.md`), through the
pinned `agent-device` CLI.

The app uses only modules that Expo Go ships, so Expo Go can run it for a quick
look. `expo-dev-client` is installed for the native development client, which
every native module beyond Expo Go's set requires.

Run the native compatibility and repository checks with:

```sh
bun --filter @stll/mobile doctor
bun --filter @stll/mobile typecheck
bun --filter @stll/mobile lint
bun --filter @stll/mobile build
```

The app intentionally shares the repository's React 19 patch release. React
Native 0.86 supports that range, and using one copy prevents Metro and native
autolinking from seeing duplicate React runtimes. Expo's exact bundled React
pin is therefore excluded from its package-version comparison; all native
module versions remain checked.

Expo Metro requires Babel 7 while the web build uses Babel 8. Both workspaces
declare their required major directly, and the workspace-hygiene check ratchets
that deliberate split while Sherif continues checking every other dependency.

Native `ios/` and `android/` directories are generated by Expo prebuild and
stay uncommitted until a capability requires maintained native source.

## TestFlight

The `Release Mobile iOS` workflow builds `preview` or `production` on a hosted
macOS runner from `main` and uploads it to TestFlight, numbering each build
with its run number and stamping the native fingerprint
(`bun scripts/fingerprint.ts ios`) as the build's runtime version. Signing is
explicit and CI never changes it: the Apple
Distribution certificate (`MOBILE_DISTRIBUTION_CERT_P12`, with its password)
and each variant's App Store profile (`MOBILE_PROFILE_PRODUCTION`,
`MOBILE_PROFILE_PREVIEW`) are created once by hand, and `app.config.ts` signs
the app target with the profile when `APPLE_TEAM_ID` and
`MOBILE_PROFILE_UUID` are set. The upload authenticates with an App Store
Connect API key of its own, with the App Manager role
(`MOBILE_ASC_API_KEY_ID`, `MOBILE_ASC_API_ISSUER_ID`, `MOBILE_ASC_API_KEY_P8`).

## Over-the-air updates

`preview` and `production` builds check `api.stll.app/v1/mobile/updates/<variant>`
on launch and run a newer JavaScript bundle from the next launch, but only one
built for their native fingerprint and signed by the update signing key. The
`Publish Mobile Update` workflow exports, signs and uploads an update to the
downloads CDN; the API route relays its signed manifest unchanged. A change to
native code needs a new TestFlight build first, which the `Mobile Fingerprint
Check` reports on its pull request.

A simulator's development client is rebuilt only when the fingerprint moved:

```sh
bun scripts/native-client.ts ensure ios <simulator-udid>
bun scripts/native-client.ts check android <emulator-serial>
```

The signing certificate is `certs/mobile-update-signing.pem`; a build without
it ships with updates off. To create the key pair once (the private key goes
to the `MOBILE_UPDATE_SIGNING_KEY` secret and nowhere else):

```sh
bunx expo-updates codesigning:generate \
  --key-output-directory "$TMPDIR/update-keys" \
  --certificate-output-directory "$TMPDIR/update-certs" \
  --certificate-validity-duration-years 10 \
  --certificate-common-name "stella mobile updates"
cp "$TMPDIR/update-certs/certificate.pem" certs/mobile-update-signing.pem
gh secret set MOBILE_UPDATE_SIGNING_KEY < "$TMPDIR/update-keys/private-key.pem"
rm -rf "$TMPDIR/update-keys" "$TMPDIR/update-certs"
```
