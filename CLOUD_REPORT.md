# Incremental case-law coverage evidence

## Implementation

`20261030222000_case_law_population_counts` adds provider-independent populations, row projections and a durable seed checkpoint. Decision statement triggers project INSERT/UPDATE/DELETE transitions and group signed deltas before updating counts, once per affected key per transition event. Keys are locked in deterministic order. Bulk writes avoid repeatedly rewriting the same count tuple for each decision. Unchanged classification produces zero deltas and leaves count tuples untouched. Projection activity timestamps support coverage's indexed court activity reads without returning to the decision table.

The single aggregate owner supplies country/court/year browse facets, validated coverage year bounds and pending-text counts. Both search configurations use it. The old facet snapshot remains as an inert rollout table; its recount writer and empty-snapshot corpus fallback are removed. Public coverage still reads `stella_case_law_coverage_summary_v2` by primary key. Source redistribution is checked at read time and in public-reader RLS.

The one-time online repair uses `createBackfillRuntime` and the shared heavy-work slot: one short transaction per source-scoped keyset batch, 128 initial rows and 256 maximum, explicit five-second statement and one-second lock deadlines. It persists source/decision cursors atomically with projections. Seed/write overlap and replay converge through the projection primary key. Reads reject an unfinished seed rather than publishing partial counts. The existing durable backfill hold (`database_backfill_states.batch.holdUntil`, `heldSince`) pauses this repair before its next batch. No corpus rewrite or migration-time backfill occurs; both new indexes build through `ONLINE_MIGRATION_INDEXES`.

The isolated schema clones decisions, sources, extraction state, scopes, revisions and revision registry, repair cursors, and scope transitions. The measurement obtains the production function with `pg_get_functiondef` and changes only its function schema and `search_path`, so it resolves those cloned relations. Both supported scopes (`CZE/cs`, `SVK/sk`) are active at generation 1 with desired revision 2, valid registry entries, completed `state-seed` and `scope-bootstrap` checkpoints, and no incomplete transitions. There is one completed extraction state per decision; 128 CZE states are pending with a fixed `pending_since`, nonempty content hashes, and redistributable source policy. That exact pending set stays fixed when the corpus doubles. Every measured call asserts `availability='available'`, CZE pending count 128 (or 1,280 in the diagnostic), and SVK pending count 0. These are active count-branch measurements, not the function's inactive/unseeded shortcut.

Actual emitted SQL:

```sql
select scope.country, pending.availability, pending.pending_count,
  pending.oldest_pending_at::text, pending.sampled_at::text,
  pending.revision, pending.scope_generation::text
from (VALUES ($1::text, $2::text), ($3::text, $4::text))
  AS scope(country, language)
CROSS JOIN LATERAL read_case_law_provision_pending(
  scope.country, scope.language, ARRAY[$5, $6, $7, $8]::text[]
) AS pending
```

Bindings 1–4 are `CZE`, `cs`, `SVK`, `sk`; bindings 5–8 are the unchanged production `EMPTY_CORPUS_CONTENT_HASHES`. The JSON evidence records their exact values.

Committed planner settings, one warmup and five `EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT JSON)` samples were used. Shared pages count hits plus reads. Other perf work ran in a different fixture/database on the same local cluster, so elapsed times are diagnostic.

### MCP transport bindings

`handlers/mcp/routes-core.ts` mounts the JSON-RPC transports outside `/v1`: POST `/mcp`, `/mcp/advanced`, `/mcp-anonymized`, `/mcp-documents`, `/mcp-law`. Transport modes filter their available tools; a POST that dispatches an available case-law/search/reader-annotation capability reuses that capability's SQL owners above. Discovery GET/OPTIONS routes do not read decisions.

The document-block reader originally listed as a generic reader-annotation HTTP dependency is **agent-only**: `mcp/reader-annotation-tools.ts` `resolveTargetForAgent` -> `handlers/legal-reader/annotations/document-blocks.ts` `resolveAnnotationTarget` -> subject lookup and published-decision AST/source by-id lookup. It is used by `list_reader_annotations`, `create_reader_annotation`, `update_reader_annotation`, and `delete_reader_annotation` when `targetType='decision'`. The related API paths remain the transport paths; tool names identify dispatch, not invented HTTP routes.

### Explicitly inspected non-read paths

- POST `/v1/search/facets` calls the closed editor/mimeType/workspace facet reader, which reads tenant entity/matter search projections, not corpus decisions. POST `/v1/search/refine` validates query syntax and builds an AI refinement; it does not run global search.
- GET `/v1/chat/decision-threads/:decisionId` only queries `chat_threads` for the caller's conversation; it does not read the decision. GET `/v1/chat/threads/:threadId/turns/:turnId/resume` returns the status/probe before run-log replay and does not invoke the withdrawal projection.
- Reader-answer PATCH/DELETE mutate the answer row and do not load the decision. Public-law annotation HTTP POST/PATCH/DELETE mutate tenant annotations; the agent target-resolution gate above is a separate MCP path.
- Account-data export POST `/v1/me/data-exports/` enqueues a BullMQ export; its request does not scan the corpus. The asynchronous export archive worker's page reader (`lib/account-export/pages.ts`) does perform withdrawal-status probes before writing copied chat/answer content. It is a queue worker, not a task in the scheduler registry. Status/download routes serve export metadata or the generated archive.
- CLI maintenance scripts and daemon ingestion/index workers are not mounted request paths or registered scheduler tasks. Their queries are outside this requested scheduler/request census.

Counterexamples inspected so import reachability is not mistaken for an executing corpus read:

- `search.repairProjections.oneMinute` (`search.repairProjections`): its repair map is closed over `contact`, `entity`, `workspace` in `lib/search/projection-repair-queue.ts`; those write-side functions in `index-global.ts` do not call its global search reader.

- `search.repairSemanticTimestamps` task: keysets `entities`, `search_documents`, preview passages and projection-repair queue; rebuilds tenant entity projections only.
- `corpusIndex.backfillJobDetail.v1`: updates `case_law_index_jobs`/statute index job diagnostic columns, not decisions or browse counts.
- `chat.sweepRunLogs`: imports the run-log owner, but calls only `sweepClosedChatRunLogs`; that retention function deletes log entries/headers and does not invoke the replay copy-projection reader.
- `memory.curator.nightly`: curates `ai_memories`; the extractor, not curator, loads compaction source text.
- `flow.run.<definitionId>` (`flow.run`): validates definition and target matter then starts/enqueues the automated flow. It is not a fixed corpus-query task. - `scheduler.dispatchBullMq`: enqueues the named job; it performs no corpus SQL itself. Public corpus ingestion/indexing and account-export workers are separate queue/daemon owners, not additional hidden scheduler corpus aggregations.
